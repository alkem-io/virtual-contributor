# 17. Faithfulness validation by context sufficiency, not content matching

Date: 2026-08-14

## Status

Accepted. Ships off by default (`FAITHFULNESS_VALIDATION_ENABLED=false`), observation only.

## Context

Nothing detected an answer stating something no retrieved evidence supported.
[vc#27](https://github.com/alkem-io/virtual-contributor/issues/27) proposed four mechanisms and
recommended layering them: **D** citation verification first (zero latency), then **B** a local NLI
model, then **A** an LLM judge run asynchronously. **C** self-consistency was rejected in the story
itself for multiplying generation cost.

Three of the four cannot be built here, each for a different reason.

**Option D has an unmet prerequisite.** Develop prefixes retrieved chunks with `[source:N]`, but no
generation prompt asks the model to cite anything — the only attribution strings in the entire
prompt corpus are ingest-side *prohibitions*. There is nothing to verify against. Citation grounding
is [#109](https://github.com/alkem-io/virtual-contributor/pull/109), open and unmerged.

**Option B needs hardware that does not exist.** `cross-encoder/nli-deberta-v3-base` requires
`torch`: multiple GB of wheels into a distroless runtime image with a size floor (workspace#026), on
pods with no GPU — `grep -rn "nvidia.com/gpu" infrastructure-operations/` returns nothing in any
cluster.

**Option A is not local.** `EMBEDDINGS_ENDPOINT` and `BOK_LLM_BASE_URL` point at
`api.scaleway.ai`; `SUMMARIZE_LLM_PROVIDER` and `ASSISTANT_LLM_PROVIDER` resolve to Mistral. A judge
would call one of them. This also means AC#4 — *"All validation runs locally — no content sent to
external APIs"* — was already false before this change: every answer is generated by a third-party
API from context that already transited to one.

## Decision

**A fifth option: detect the single case that is provable for free — an assertive answer produced
when retrieval returned nothing — behind a port that the other mechanisms can occupy later.**

### Word-overlap scoring was built, measured, and rejected

The obvious deterministic alternative is to check whether the answer's content words occur in the
context. It was implemented and measured against realistic pairs, because a check that fires on
faithful answers is worse than no check — it becomes noise people learn to ignore:

```
faithful paraphrase                 overlap 0.22–0.56
"I don't have enough information"   overlap 0.00   <- correct behaviour
fabrication                         overlap 0.00
```

No threshold separates them. Any cutoff catching the fabrication also condemns the honest refusal —
the model doing exactly what it was instructed to do. And because the platform answers in the
member's language (`"Answer in {language}"`), a Dutch answer over English context scores 0.00 as
well: the check would have flagged **every non-English answer on the platform**.

### What context sufficiency gives instead

An answer asserting content when retrieval returned nothing is unambiguously unsupportable — there
was no evidence, so whatever it says came from somewhere else. The decision order is load-bearing:

1. context present → supported
2. empty answer → supported
3. hedged answer → supported
4. otherwise → not supported

Checking context **first** is what makes paraphrase and translation *structurally incapable* of
being flagged, rather than merely unlikely to be. And hedge detection can only ever *suppress* a
flag, so a gap there costs one spurious log line — never a wrongly-approved answer.

### Two implementation traps, both found by walking the code

- **The two plugins represent "no context" differently.** Expert yields `""` from `"\n".join([])`;
  guidance substitutes the literal `"No relevant context found."`. Handling one silently does
  nothing for half the traffic.
- **The expert graph path returns `sources=[]` by design.** Keying the check off `Response.sources`
  would have flagged 100% of graph-path answers. It keys off the context string.

### Flagging is internal

AC#5 permits flagging "either to user or internally". A caveat attached to an answer is a product
decision with a visible surface; a log record is a diagnostic. This ships the diagnostic — the
frequency of zero-context answers in production is unknown, and measuring it is what makes any
member-facing decision informed rather than speculative.

## Consequences

- Free and local: no model, no dependency, no network call. Under 5 ms on a 10 MB answer; effectively
  zero on the common path where context is present.
- **Observation only.** The answer a member receives is byte-identical whether or not a flag fires,
  and a validator that raises cannot cost anyone their answer. Both asserted.
- Off by default; disabled means no validator is constructed at all, so the rollback is structural.
- **It does not catch a fabrication built on thin-but-nonempty context.** That needs citations or a
  judge. The port exists so either drops in without touching plugin code — which is the reason to
  ship the seam now rather than wait for #109.
- Hedge detection is English-only. The failure mode is one spurious internal log line, never a
  member-visible change.
- No egress on this path, enforced by a transitive import scan over *every* implementation of the
  port, a socket-poisoned runtime test, and a manifest guard. That is a claim about the validation
  step, not about the service: generation already sends the same answer and context to a third party.
